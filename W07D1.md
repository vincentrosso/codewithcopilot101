## About this week — the capstone's headline feature

Brand Lens was always going to "evaluate a brand's US presence using web scraping, structured data, and LLM-generated briefs." You've built the scraping (Weeks 1–4), the structured data (Week 6's database). This week the third piece arrives: the LLM, *inside the codebase*, not as a tool you chat with.

The difference is the whole lesson. When you use Copilot CLI, a human (you) reads the answer and decides what to do. When your *program* calls a model, there's no human in the loop at call time — the code sends data, gets a response, and has to do something sensible with it automatically, including when the response is weird or the call fails. That changes how you write it.

## 2. What you're about to do (~5 min)

An **API** (Application Programming Interface) is a way for one program to ask another program — usually over the internet — to do something. GitHub runs language models on its servers — **GitHub Models** — and exposes an API: your program sends an HTTP request containing your prompt, their server runs the model, and sends back the response. It's the same request/response shape as `requests.get` from Week 1 (W02D3) — you're just talking to GitHub's model servers instead of a brand's website, and the `openai` package handles the HTTP details for you.

(Why a package called `openai` when you're talking to GitHub? Because OpenAI's request format became an industry standard, and GitHub Models speaks it. The `openai` package can talk to any server that speaks that format — you just tell it *which* server. You'll see that on one line below.)

Two things make it different from fetching a web page:

- **It's metered.** Each call is measured by the amount of text in and out (D3 explains "tokens"). On GitHub's free tier you don't pay — instead you get **rate limits**: a cap on requests per minute and per day, and on how much text one request can carry. Small models allow more requests than big ones. Plenty for this course; not enough to be careless. (If an account turns on paid usage, the same meter becomes a bill.)
- **It needs a secret token.** The API has to know it's you. That token is like a password. Anyone who gets it can use your quota as you. So the entire first half of today is about handling that token correctly — getting it, and making sure it never, ever lands in git.

## 3. Get an access token (~10 min)

GitHub Models authenticates with a **personal access token** — a long string that acts as a password for one specific job. You'll make one that can do *only* that job.

1. Go to **github.com/settings/personal-access-tokens/new** (GitHub → your avatar → Settings → Developer settings → Personal access tokens → **Fine-grained tokens** → Generate new token).
2. **Token name:** `brand-lens-models`. **Expiration:** 90 days is fine.
3. **Repository access:** choose **Public repositories** (read-only). Your code doesn't need to touch any repo.
4. **Permissions:** find **Models** and set it to **Read-only**. Leave everything else at "No access."
5. Generate. It looks like `github_pat_...` — a long string.
6. **Copy it once, now.** GitHub shows it a single time. If you lose it, you make a new one; you can't view the old one again.

Step 4 is a security decision, not a formality. This token can call models and nothing else — it can't push to your repos, delete anything, or read private code. If it leaks, the damage is limited to someone using up your model quota. Granting *only* what's needed is called **least privilege**; you'll meet the same idea, with higher stakes, when you set up AWS in Week 11.

Do **not** paste it into a chat, a file you'll commit, or a screenshot. Treat it like a password, because functionally it is one.

Before leaving GitHub, visit **github.com/marketplace/models** and click the model you'll use today, **OpenAI GPT-4.1-mini**. The page shows the model's ID (`openai/gpt-4.1-mini`), a playground where you can try prompts, and its rate limits. Note the limits in your journal — you'll want them on D3.

## 4. Store the key safely with a .env file (~15 min)

You never put secrets in code. The standard pattern — the same one mkecitysmart and the autoarb scraper use — is a `.env` file that holds secrets, is read at runtime, and is **never committed**.

(One Copilot CLI note: it can read files in your folder, and `.env` is a file in your folder. Don't ask Copilot to "look at my .env," never approve a command like `cat .env`, and if it ever prints a token back to you, revoke that token on GitHub and make a new one. And never paste the token into the Copilot app either.)

First, make sure git ignores it. Open `.gitignore` (you made one on W06D1) and add:

```
.env
```

**Do this before creating the .env file**, so there's no window where it's trackable.

Now create the file:

```
touch .env
code .env
```

Put your token in it — one line, no quotes, no spaces around the `=`:

```
GITHUB_MODELS_TOKEN=github_pat_your-actual-token-here
```

Save. Then confirm git is ignoring it:

```
git status
```

`.env` should **not** appear in the list of changes. If it does, your `.gitignore` line is wrong — fix it before going further. This is the single most important check of the day.

It's good practice to commit a *template* that shows what the file should contain, without the secret:

```
touch .env.example
code .env.example
```

```
GITHUB_MODELS_TOKEN=github_pat_...
```

`.env.example` is safe to commit — it has no real token, just the shape. Anyone setting up the project later copies it to `.env` and fills in their own.

## 5. Install the packages (~5 min)

```
pip install openai python-dotenv
```

- **`openai`** — the official Python SDK for the OpenAI-style API, which GitHub Models speaks. It wraps the HTTP calls so you write Python, not raw web requests.
- **`python-dotenv`** — reads your `.env` file and loads the values into the environment when your program starts. Without it, your program wouldn't see `GITHUB_MODELS_TOKEN`.

If you keep a `requirements.txt`, add both.

## 6. Your first call (~20 min)

```
touch first_call.py
code first_call.py
```

```python
import os
from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()                 # read .env into the environment

client = OpenAI(
    base_url="https://models.github.ai/inference",
    api_key=os.environ["GITHUB_MODELS_TOKEN"],
)

response = client.chat.completions.create(
    model="openai/gpt-4.1-mini",
    max_tokens=300,
    messages=[
        {"role": "user", "content": "In one sentence, what is a brand's value proposition?"}
    ],
)

print(response.choices[0].message.content)
```

Read every line:

- **`load_dotenv()`** — reads `.env` and makes `GITHUB_MODELS_TOKEN` available. Must run *before* you create the client.
- **`os.environ["GITHUB_MODELS_TOKEN"]`** — reads the token out of the environment (where `load_dotenv` just put it). `os.environ` behaves like a dict. You never write the token in the code — the code *looks it up*. If the name is wrong or `.env` didn't load, this line raises a `KeyError` that names the missing variable — a loud, clear failure, which is what you want.
- **`OpenAI(base_url=..., api_key=...)`** — the client object. `base_url` is *which server* to talk to: GitHub's model servers, not OpenAI's. Change that one string and the same code talks to a different provider. `api_key` is the token that proves it's you.
- **`model="openai/gpt-4.1-mini"`** — *which* model. GitHub Models hosts models from several companies; the ID is `publisher/model`. GPT-4.1-mini is small and fast — plenty for learning and for short brand summaries, and small models get the most generous free limits. (Bigger models exist for harder work. You'd change one string.)
- **`max_tokens=300`** — the most text the model is allowed to generate in the reply. A safety cap: it stops a runaway response from eating your limits. (D3: a token is roughly ¾ of a word.)
- **`messages=[{"role": "user", "content": "..."}]`** — the conversation, as a list. One message here, from `"user"` (you). The model replies as the `"assistant"`. This is the same chat shape you've used in the Copilot app, written as data.

- **`response.choices[0].message.content`** — digging the text out of the response. The reply is an object; `.choices` is a list of possible answers (you asked for one, so there's one); `[0]` is the first; `.message` is the assistant's message; `.content` is its text. You'll meet this shape again, so don't gloss over it.

**Predict before you run.** Write in your journal, in one sentence, what you expect the model to say. Then:

```
python3 first_call.py
```

You should see a one-sentence answer about value propositions. **That used one request of your daily limit, and you just called an LLM from inside a program for the first time.**

If you get an error instead: a `KeyError: 'GITHUB_MODELS_TOKEN'` means `.env` didn't load (wrong name, wrong folder, or `load_dotenv()` missing). A `401` / `AuthenticationError` means the token is wrong or lacks the Models permission. A `429` / `RateLimitError` means you've hit a limit — wait a minute. Read the last line of the traceback; it usually says which.

## 7. Run it again — and notice something (~5 min)

Run it a second time:

```
python3 first_call.py
```

The answer is *similar but not identical* to the first run. Same question, different wording. This is important and it's nothing like the code you've written all course: `parse_page` returns the exact same dict every time for the same input (it's *pure*, W05D3). An LLM call does not. Given the same prompt, you get a *different* response each time.

If your section-6 prediction assumed you could guess the exact wording, edit your journal: **you can't.** This non-determinism is the single biggest thing that makes LLM calls different to program around, and it's why testing them (D4) needs a special trick. Note in your journal how the two runs differed.
