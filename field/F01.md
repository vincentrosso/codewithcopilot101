# Field Notes 1 — One day, one client: a phone-first login for a Shopify store
*v1.0.0*

**Goal for today:** read what one real working day at NIT America looked like — a small retail client's Shopify site, an AI coding agent driving — and come out able to explain the five pieces that got built, why each one lives where it lives, and the three places Shopify said no. Then, optionally, reproduce the Shopify half yourself in a free development store. No AWS account needed.

**Time budget:** ~75 min reading and notes, ~90 min optional hands-on, ~20 min journal.

A note on tools: the day written up here was worked with **Claude Code**, a different AI coding agent, and this note keeps the history as it happened. Every habit in it carries over to Copilot CLI — the two tools work the same way: a terminal session in a repo, diffs shown before writing, approval before commands — and the hands-on in section 9 uses Copilot CLI. Where the two tools behave differently, it says so.

This is not a course day. Nothing here advances Brand Lens. It is a field note: the shape of a day's work, with the decisions left in. Read it the way you'd read a colleague's post-mortem — slowly, and asking at every step *"why there?"*

## 0. The ask (~5 min)

The client is a small wellness shop in LA's Koreatown with a Shopify web store. They are an SMS client of ours. Vincent's direction, in one sentence:

> Write our own sign-in, phone first, email second; consent by checkbox at sign-up; the point is capturing phone numbers for SMS campaigns; and a loyalty program that pays customers for referrals.

Read that twice. Notice what it is *not*: it is not "add a login to the Shopify store." It is "get the phone number and the consent, and make referrals pay." The login is the door; the phone number is the goal. Every decision below falls out of that sentence, and most of the day's mistakes would have come from forgetting it.

**The first thing we learned, before writing a line:** Shopify customer accounts are **email-only** (classic accounts = email + password; new accounts = email + 6-digit code). Signing a customer in from *our* side, or by phone, needs **Multipass**, which is a Shopify Plus feature at roughly $2,300 a month. So a phone-first login *cannot be a Shopify login* on this store.

That one fact decided the architecture. The login would be a **member** login that lives in our stack and sits *beside* Shopify checkout, not inside it. That is fine — reread the ask — because the goal is the phone number and its consent, not a Shopify session.

## 1. The map (~10 min)

Five pieces. Keep this picture open while you read the rest.

```
 shopper's browser on the client's storefront
 ────────────────────────────────────────────
   [1] the THEME — Liquid + JS, pushed with Shopify CLI
       a sign-in modal: phone → code → consent → (email)
            │  fetch()  JSON, Bearer token in localStorage
            ▼
   [2] our members API — API Gateway → Lambda → DynamoDB   (AWS, ours)
       POST /members/otp · /verify · /consent · /email · GET /members/me …
            │                       │
            │ SMS (the code,         │ Admin GraphQL (mirror the member as a
            │ the welcome,           │ Shopify Customer; mint discount codes)
            ▼ the rewards)           ▼
       SMS provider            [3] the SHOPIFY APP — made in Shopify's Dev
                                   Dashboard; gives [2] a client id + secret
                                   and a list of permissions (scopes)
                                        ▲
                                        │ [4] WEBHOOKS back the other way:
                                        │     customers/update, orders/paid
                                        │     → POST /members/shopify-webhook/<client>
   [5] REFERRALS — a 5-char code per member, ?ref=CODE on the storefront,
       $20 friend / $20 advocate as single-use Shopify discount codes
```

Three things to notice about the shape before any detail:

- **The logic lives in [2], on AWS, not in Shopify.** A Shopify app cannot host code — only checkout/discount *Functions* and static theme blocks run inside Shopify. Anything that texts, stores, or decides runs on our side.
- **[2] is the same small service that already serves our opt-in pages**, not the main NIT backend. The main backend can be *parked* (scaled to zero to save money). A retail-facing surface — something a shopper touches — has to answer at 2am on a Sunday. That rule predates this day; this day just reused it.
- **Shopify talks to us in both directions.** We push members *in* ([3]); Shopify pushes changes *back* ([4]). Two-way means you have to handle your own echo — more on that in section 5.

## 2. The theme — Shopify CLI, not the online editor (~15 min)

Shopify has a code editor in the admin. We did not use it. We used the **Shopify CLI**, which turns a theme into files on disk:

```
npm i @shopify/cli@latest
npx shopify theme list --store <store>.myshopify.com                 # which theme is live?
npx shopify theme pull --store <store>.myshopify.com --theme <id>    # download it
```

Authentication is a device code: the CLI prints a URL and a short code, you open it in a browser where you are already logged into the store, approve, done. No password ever touches the terminal.

**Why files beat the online editor** — the same reason Week 2 put your code in a folder and Week 4 made you read diffs: once a theme is a directory, it is in git, an AI agent (Copilot, in your case) can read every file, propose a patch, and you can `git diff` the patch before it goes anywhere. The online editor gives you none of that; a Save button there is an irreversible write to a live store with no record of what changed.

The theme has a layout you'll recognize from Week 9's static site, with one new word:

```
theme/
  layout/      theme.liquid — the page skeleton
  sections/    header.liquid, member-orders.liquid …   (blocks the merchant arranges)
  snippets/    member-signin.liquid, lang-switch.liquid (reusable fragments)
  templates/   index.json, index.orders.json            (which sections on which page)
  assets/      theme.js, theme.css
  config/      settings_schema.json — what the merchant can set in the admin
  locales/
```

**Liquid** is Shopify's template language — the same job as `jinja2` in Week 8, different syntax: `{{ section.settings.members_api }}` instead of `{{ brand.name }}`, `{%- if … -%}` instead of `{% if %}`.

### What changed in the theme that day

1. **Three languages.** The theme was already bilingual EN/한 by a home-made mechanism: every piece of text is a *pair* of settings, `title_en` / `title_kr`, and a CSS class on `<html>` decides which one shows. The owners' first language is Chinese, so Simplified Chinese was added — every pair became a triple with a `_zh` sibling, and a small Python script did the mechanical part: walk the JSON, find every `_en` key, add the `_zh` twin. One rule written into the code: **Korean and Chinese fall back to English when blank.** That rule also fixed a bug nobody had reported — several Korean call-to-action buttons were rendering *empty*, because their `_kr` setting had never been filled in.

2. **The sign-in modal** — `snippets/member-signin.liquid`, four steps as four `<form data-member-step="…">` elements (phone → code → consent → done), one visible at a time, plus an optional email step. `theme.js` drives them: a `fetch()` wrapper that adds the Bearer token, a tiny state machine that hides one step and shows the next. The API base URL and the client's slug are **header settings** (`members_api`, `members_slug`) so the theme can be pointed at a different backend from the admin, without touching code.

3. **A real Orders page** — `templates/index.orders.json` + `sections/member-orders.liquid`, reachable only when signed in.

### Two things that bit us

- **Shopify strips settings keys it doesn't recognize yet.** We pushed the *values* file (which API URL, which slug) in the same push as the section file whose `{% schema %}` *declares* those settings. Shopify processed the values before the schema, saw two unknown keys, and silently dropped them. The fix was to push the values file again *after* the schema had landed. General shape: **when a system validates data against a schema, the schema must exist first.** You have seen this before — a SQLite `INSERT` into a column the `CREATE TABLE` hasn't added yet.

- **Claude Code refused to push to the live theme.** The command was `shopify theme push --allow-live`; Claude's permission classifier judged "write to a production store" as something a human should do, and declined. So the push lives in a one-line script that Vincent runs himself. Note what did *not* get refused: `shopify theme push --unpublished`, which creates a draft theme you can preview at a private URL. That is the right tool for *"show me before it's live"* anyway. **A tool that refuses an action is doing its job; the response is a preview path and a human on the live button, not a workaround.**

  *In Copilot CLI:* don't count on a classifier making this call for you. The command appears in an approval prompt, and **you** are the classifier — which is exactly why the Week 4 rule says never approve a command you can't explain, and never pick "approve for the rest of the session" or start with `--allow-all-tools`. A push with `--allow-live` gets **No**, every time. (Copilot CLI also has a `--deny-tool` flag that blocks a command outright — worth a look once you're comfortable.)

## 3. The login — the AWS half (~15 min)

The Lambda got a new family of routes. Read the table as the *contract* — the theme is one client of it; a mobile app or a kiosk would be another.

| Route | Who calls it | What it does |
|---|---|---|
| `POST /members/otp` | theme, phone step | texts a 6-digit code to the phone |
| `POST /members/verify` | theme, code step | checks the code → returns a signed token + the member. New phone = new member, and the theme is told to show the consent step |
| `POST /members/consent` | theme, consent step | writes **one consent row** through the same queue the opt-in pages use — same labels, same wording, verbatim |
| `POST /members/email`, `/email/verify` | theme, optional | a 6-digit code by email; email becomes "proven" |
| `GET /members/me` | theme, every page load | who am I, from the token |
| `GET /members/orders` | theme, Orders page | the member's Shopify orders (needs the app's `read_orders`) |
| `GET /members/referral` | theme, panel | the member's code, link, counts |
| `POST /members/shopify-webhook/<client>` | Shopify | section 5 |

Decisions worth being able to defend:

- **Identity is `(client, phone)`.** One member row per phone per client, in DynamoDB. Email is optional at sign-up. The phone *is* the account — which is exactly backwards from Shopify, and exactly what the ask said.
- **Sign-up and sign-in are the same screen.** The code step doesn't know or care whether you're new. Only *after* a successful code does the server say "new — show them consent."
- **The consent step uses the opt-in page's exact checkbox labels.** The SMS carriers grade the *label the shopper saw* when they review a campaign; a paraphrase is a compliance risk. **Unticked = no consent, but the member is still created** — they can log in, see orders, use referrals; they just get no marketing texts. Consent is a *separate* yes, never bundled into "sign up."
- **Rate limits were copied, not invented:** a handful of codes per phone per hour, a larger cap per IP, a 10-minute code expiry, a few wrong guesses. The main backend already had a two-stage limiter on its own OTP route and had already taught us (painfully, in a live demo) what happens without one.
- **The session is a signed token in `localStorage`**, 24 hours. Not a cookie, because the storefront is on the client's domain and the API is on ours — cookies don't cross domains; a header does.
- **Reuse, not rewrite.** The main backend already has phone + email OTP. Its logic was *lifted* into the Lambda; the backend itself was not pointed at retail shoppers, because (a) it creates NIT platform users, which a shopper is not, and (b) it parks.

Tests: 18 for the member routes, run with plain `node`, no framework. Same W5 principle: the first one written by hand set the standard; the rest were reviewed diff by diff.

**Deployed with Terraform** (the W11/W12 idea — infrastructure as files in git, applied by a command), with one house rule: push to the shared branch *before* applying from a laptop, because the next automated apply uses what is on that branch, and state that is ahead of it gets rolled back mid-flight. Proven end to end the same afternoon: a sign-in from the live site on a test phone → member row → consent row → welcome SMS as the client → a Shopify Customer created with phone and SMS consent subscribed.

## 4. The Shopify app — Dev Dashboard, scopes, and the lesson about scopes (~15 min)

Why have an app at all? Because a member who exists only in our database is invisible to Shopify: checkout won't pre-fill their phone, Shopify's own SMS-consent record won't exist, and a loyalty app keyed on Shopify customers can't see them. So on consent, the Lambda **upserts a Shopify Customer** with phone, email if any, and `smsMarketingConsent: SUBSCRIBED`, through the Admin GraphQL API. To call that API you need credentials, and credentials come from an **app**.

### The 2026 wrinkle

Older Shopify tutorials show a "custom app" that hands you a static access token starting `shpat_`. **For apps created after January 2026, that is gone.** The Dev Dashboard gives you a **Client ID + Client secret**, and your code trades them for a 24-hour access token itself — the *client credentials grant*:

```
POST https://<store>.myshopify.com/admin/oauth/access_token
     client_id=…&client_secret=…&grant_type=client_credentials
→ { "access_token": "…", "expires_in": 86399 }
```

Then every API call carries `X-Shopify-Access-Token`. The Lambda does this on demand and **caches the token in memory for the day**. Hold that thought.

This grant only works because the app and the store belong to the *same* Shopify organization — the app was created under the store owner's login. For a client who won't give us that, the longer road is a proper OAuth install; not needed today.

### The clicks (the half that is not scriptable)

Store admin → Settings → Apps and sales channels → Develop apps → **Build apps in Dev Dashboard** → accept the developer terms → Apps → **Create app** → **Versions → create a version** with the scopes you need → release → **Distribution → Custom** → enter the store → generate the install link → open it → **Install** → **Settings** → copy Client ID + Client secret → store them in a secrets manager, one entry per client, never in a file. The Lambda reads that entry; until it exists, the mirror logs a clearly named "skipped" line and nothing else changes — **a missing credential degrades one feature, loudly, instead of breaking sign-in.**

### The scope lesson — this is the one to remember

Scopes are the app's permissions: `read_customers`, `write_customers`, `read_customer_events`, `read_orders`, `write_discounts`. The app started with two and needed more as the day went on (orders in the afternoon, discounts near the end). Each time, the same three-step trap:

1. **Releasing a new app version with the new scope is not enough.** The *store* has to accept the new permission. Opening the app from the store's Apps page did *not* prompt. What worked: Dev Dashboard → the app's Overview → **Install app** → pick the store → Shopify shows "Update data access" → Update.
2. **Then the Lambda's cached token still has the old scopes** — it is good for 24 hours and it was minted before the change. Redeploy the function (same code, fresh process) or wait a day. A real bug-shaped hour was spent on "but I granted it" before this clicked.
3. The version half *is* scriptable with the CLI, from a `shopify.app.toml`:

```toml
client_id = "<the app's client id>"
name = "<app name>"
application_url = "https://<your api>/members/app"
embedded = false

[access_scopes]
scopes = "read_customers,write_customers,read_customer_events,read_orders,write_discounts"
```

```
shopify app deploy --no-input --allow-updates --message "add write_discounts (referral codes)"
```

The general lesson, which you will meet again with Google, Meta, AWS IAM and every OAuth system: **a permission has three states — declared, granted, and in-hand.** Changing the first does nothing until the second happens, and the second does nothing while something is still holding the third. When "I added the permission" and "it still says forbidden" are both true, ask which of the three you actually changed.

One more: `application_url` has to answer something. The app's "open" link in the admin used to return an error; it now returns a one-paragraph page. Small, but a merchant clicking a broken link is how trust goes.

## 5. Two-way — webhooks, and handling your own echo (~10 min)

Section 4 pushes members *into* Shopify. But a shopper can also tick "text me" at Shopify's own checkout, a merchant can edit a phone in the admin, a customer can unsubscribe. Those happen in Shopify and we'd never know. So three **webhooks** were registered (by API, not by clicking): `customers/create`, `customers/update`, `orders/paid` → `POST /members/shopify-webhook/<client>`, each request signed with an HMAC whose key is the app's client secret (the QA sideline's rule: verify the signature *before* reading the body).

The mapping rules matter more than the plumbing, because they are compliance decisions:

| Shopify says | We record |
|---|---|
| SMS subscribed, **by the shopper at checkout** | a *marketing* consent row (the shopper ticked it themselves) |
| SMS subscribed, **set by the merchant or an app** | *transactional-only* consent — the same rule as when a business uploads its own customer list: they may text you about your order, not about a sale |
| SMS unsubscribed | an opt-out row |
| name / email edited | the member record updated; a merchant-typed email counts as proven |

**The echo problem.** We write a customer to Shopify (section 4). Shopify fires `customers/update` *about our own write*. If we process it, we write again, Shopify fires again. The guard: ignore an update whose content matches what *we* sent within the last 60 seconds, and record each `(state, consent_updated_at)` pair once. Any time a system is both a writer and a listener on the same object, draw this loop before you write the handler.

Proven live: a tag edited on a test customer record came back through the webhook within seconds.

## 6. Referrals — why not the app store, and what we built instead (~10 min)

The obvious move was **Smile.io**, the standard Shopify loyalty app, Free tier. It was researched first and installed (points on orders; a referral program at $20/$20) — and then the referral half was built by hand anyway. Why:

- Smile is **keyed on email**. It has no phone identity at all. A member who gave us only a phone doesn't exist to it.
- Its referral links are only readable programmatically on the **$999/month** plan. So on Free we could never put a member's own referral link into a text message — and texting is the whole point.

So Smile stays as a *points* layer the owners can keep or drop, and referrals are ours:

- Every member gets a **5-character code** at sign-up. `<storefront>/?ref=CODE` — the theme stores the code in `localStorage` and sends it with the friend's sign-up.
- A **new** member (never yourself, never an existing phone) signed up with a code is "referred by" it. After their consent step the Lambda mints a single-use Shopify discount — `FRIEND-XXXXX`, $20 off $60+, 30 days — via `discountCodeBasicCreate` (that's the `write_discounts` scope from section 4) and texts it to them.
- When the friend's **first paid order** lands (`orders/paid` webhook), the Lambda mints `THANKS-XXXXX` $20 for the advocate and texts it. One reward per referral.
- The amounts are Terraform variables, not constants in code, so the next client can run $10/$10 without a code change.

Notice the pattern: the vendor's feature was 80% of what we wanted, and the missing 20% was the part that mattered. **Research the off-the-shelf thing first, say precisely which requirement it fails, and build only that.**

## 7. Where Shopify said no — the honest list (~5 min)

A day's write-up that only lists wins is a sales deck. These are the walls:

- **Checkout is still Shopify's.** A member session can never become a Shopify customer session without Plus/Multipass. Mitigation: a signed-in member's checkout link carries `checkout[email]` and `checkout[shipping_address][phone]` so nothing is retyped. The store setting that shows a "Sign in" link at checkout was turned off so shoppers aren't offered a second, different login.
- **Saved cards are impossible through us.** Card data never leaves Shopify Payments; that was Shop Pay's job, and the owners chose to switch Shop Pay off. Returning customers type their card.
- **A Shopify app cannot host logic.** Hence AWS. The *next* step is an app wrapper — a theme app extension (no theme edits), an app proxy so the API appears on the client's own domain, OAuth install — but it would still be the same Lambda behind it.
- **Three store settings had to be changed by hand** in the admin, and one of them was the real bug of the day: the store's only *Location* had no address, which is why "pick up in store" errored with *"No locations in United States with your item."* Not a code problem. Found by trying a real checkout.

And one honest open: "Sign in with Kakao" was built as a **third door into the same member record** (phone, email, Kakao id — one member) and is deployed but dormant until Kakao's developer console is configured. It cannot be a Shopify login either, for the same Multipass reason.

## 8. How the AI agent was actually used (~5 min)

(This was Claude Code. The Copilot equivalents are in brackets.)

- **Several sessions, split by repo** — one on the theme, one on the Terraform/Lambda, one on the Shopify app — each in its own git worktree so they couldn't step on each other's files. [Copilot CLI: the same — one terminal session per worktree.] They *could* still step on each other's **infrastructure**: two sessions applied the same Terraform module minutes apart and each reverted the other's environment variables. Lesson: **re-plan after any apply you didn't do yourself.** Files have worktrees; a cloud resource has one copy.
- **Context files as memory.** Every decision above was written into a context file in the repo *as it was made*, timestamped. That file is where this lesson came from. When the next client's store comes along, the session reads it and skips a day of rediscovery. [Copilot CLI: `.github/copilot-instructions.md` or `AGENTS.md`, which it reads at the start of every session.]
- **The refusal was a feature.** Twice the classifier declined a live write (the theme push, the Save button in Shopify's editor). Both times the answer was a script Vincent runs by hand. [Copilot CLI: you answer No at the approval prompt — same outcome, but it depends on you.] The human stays on the production button; the AI prepares everything up to it.
- **Proof was a real phone, every time.** Not "the request returned 200" — a test phone received the code, the welcome, the discount. Section 4 of the QA track: an assertion that can't fail proves nothing; a text that arrives does.

## 9. Hands-on, optional: the Shopify half in a free dev store (~90 min)

Everything below is free and touches nothing of ours. You need a Shopify **Dev Dashboard** account (dev.shopify.com — sign in with any Shopify login; accept the developer terms).

**a. A store to break.** Dev Dashboard → Stores → **Create development store** (any name, "test data" is fine). Note its `<name>.myshopify.com`.

**b. The CLI, and a theme as files.**

```
mkdir -p ~/dev/shop-lab && cd ~/dev/shop-lab
npm init -y && npm i @shopify/cli@latest
npx shopify theme list --store <name>.myshopify.com
```

Approve the device code in the browser. Pull the theme Shopify gave the store (Dawn or Horizon), into a folder:

```
npx shopify theme pull --store <name>.myshopify.com --path theme
git init && git add . && git commit -m "shop-lab: pulled the default theme untouched"
```

**c. Make a change, preview it, never go live.** Start Copilot CLI in `~/dev/shop-lab` (`copilot`) and ask:

> This is a Shopify theme pulled with the CLI. Add a "Join" button to the header section that links to a URL set in the section's schema (setting `join_url`), hidden when blank. Show me the diff before writing. Do not touch any other file.

Review the diff — it should touch one `sections/header*.liquid` (the markup *and* the `{% schema %}` block at the bottom). Then:

```
npx shopify theme push --store <name>.myshopify.com --unpublished --theme "shawna lab"
```

The CLI prints a preview URL. Open it; set the URL in the theme editor; see the button. Then, on purpose, ask Copilot to run the same push with `--allow-live` and watch what happens: the command appears in an approval prompt. Answer **No**. Write down what Copilot proposed, and what it said when you declined — then compare with the refusal in section 2.


**d. An app and a token — the section-4 trap, in miniature.** Dev Dashboard → Apps → Create app → name it → Versions → create a version with scope `read_customers` only → release → Distribution → Custom → your dev store → install. Settings → Client ID + secret. Then, in a terminal — **never paste the secret into a file you'd commit; export it the Week 7 way:**

```
export SHOP=<name>.myshopify.com CID=<client id> CSEC=<client secret>
curl -s -X POST "https://$SHOP/admin/oauth/access_token" \
  -d "client_id=$CID" -d "client_secret=$CSEC" -d "grant_type=client_credentials"
```

You get a JSON with `access_token` and `expires_in`. Now one GraphQL read:

```
export TOK=<access_token>
curl -s "https://$SHOP/admin/api/2025-07/graphql.json" \
  -H "X-Shopify-Access-Token: $TOK" -H "Content-Type: application/json" \
  -d '{"query":"{ customers(first: 3) { nodes { id phone email } } }"}'
```

**e. Now reproduce the scope lesson.** Try to *write*: ask Copilot for a `customerCreate` mutation
 with a phone and `smsMarketingConsent`. Run it. It fails — you only have `read_customers`. Add `write_customers` in a new app version, release it, and run the mutation again *with the same token*. Still fails. Go to the app's Overview → Install app → your store → "Update data access" → Update. Same token: **still** fails. Mint a new token (step d). Now it works. You have just touched all three states — declared, granted, in-hand — with your own hands. The hour we lost is now ten minutes you understand.

**f. Commit** (theme folder only; the secret is in your shell, not on disk):

```
git add theme && git commit -m "shop-lab: join button in header, previewed on an unpublished theme"
```
