# Week 4, Day 1 — Meet Copilot CLI
*v1.0.0*

**Goal for today:** install GitHub Copilot CLI, point it at brand-lens, and take a read-only tour. Three new rules — review every diff, never auto-approve a command, ask before committing unclear code — replace Week 2's two rules. By end of day Copilot CLI has explained your repo to you and you haven't accepted a single edit yet.

**Time budget:** ~75 min hands-on, ~15 min journal, ~30 min slack.

---

## About the tool — what changes today

You met Copilot in the Microsoft 365 Copilot app on W02D1. That was a chat: paste code, read explanation, type code yourself. **GitHub Copilot CLI** is the developer's version — it runs in your terminal, can read files in your repo, can edit them, and can run commands. The chat is now a colleague who has hands.

Same family name, different tools, and it's worth being clear about which is which:

- **The Copilot app** (Microsoft 365) is for business users — documents, email, questions, and explaining a pasted snippet. It never sees your repo. You'll keep using it for that.
- **Copilot CLI** (GitHub) is the real deal for code — it works *inside* `~/dev/brand-lens`, on your actual files.

That power needs new rules. Week 2 had two:

1. Ask Copilot to explain, not to write.
2. Run everything yourself.

Week 4 has three:

**Rule 1: Review every diff before accepting.** Copilot CLI shows a proposed file change as a diff (added lines marked `+`, removed lines marked `-`) and asks before writing it. Read every line. If you accept a diff you didn't read, you don't own the code — and you can't debug it later.

**Rule 2: Never auto-approve a command you can't explain.** Copilot CLI asks before running shell commands. The temptation to hit "yes" is real. Don't. If you don't know what `rm -rf node_modules` does, say no, ask why it wants to run that, then decide. Every approval prompt offers a "yes, and approve this for the rest of the session" option, and the CLI has an `--allow-all-tools` flag that skips asking entirely. Never use either in this course.

**Rule 3: If a line is unclear, ask before committing.** When Copilot CLI edits a line you don't fully understand, ask it to explain *that line* before you commit. Don't commit code you can't read.

These rules tighten as you get more access, not loosen.

## 1. Warm-up (~5 min)

Activate venv. From inside `~/dev/brand-lens`:

```
source .venv/bin/activate
python3 runner.py --limit 1
```

Confirm Week 3's pipeline still works. You'll need this baseline tomorrow.

## 2. Install Node, then Copilot CLI (~20 min)

First, one thing that isn't a command: Copilot CLI needs a **GitHub Copilot plan** on the GitHub account you made on W01D1. Ask Vincent for a seat on NIT's Copilot Business plan (or start a Copilot Pro trial yourself). The plans page at github.com/features/copilot/plans says which plans include Copilot CLI.

Copilot CLI installs via `npm`, which comes with Node.js. Install Node via Homebrew:

```
brew install node
```

This is the same pattern as W01D2 — Homebrew installs the tool, then the tool's package manager (`npm`) installs the thing you want. Verify:

```
node --version
npm --version
```

Both should print version numbers. Copilot CLI needs a recent Node — if `node --version` prints something below `v22`, run `brew upgrade node`. Now install Copilot CLI:

```
npm install -g @github/copilot
```

The `-g` flag installs it globally so the `copilot` command is available from any directory. When it finishes:

```
copilot --version
```

Should print a version number. If you see `command not found`, your shell hasn't picked up the new binary — open a new terminal tab and try again.

## 3. First session — log in (~10 min)

In your terminal:

```
cd ~/dev/brand-lens
copilot
```

Two things happen the first time:

1. **It asks whether you trust the files in this folder.** This is your repo, so yes — choose the option that trusts it for this session. (Copilot CLI asks per folder because it will read and act on whatever is inside. Get in the habit of reading that question every time, not clicking through it.)
2. **It asks you to log in.** Type `/login` if it doesn't prompt you. It shows a short code and a URL; open the URL in a browser, sign in with your **GitHub** account (not your Microsoft work account — this is the GitHub side of Copilot), enter the code, approve, and come back to the terminal.

Once logged in, you're in an interactive session inside `~/dev/brand-lens`. Copilot CLI can read any file in this directory tree. It can also edit files and run commands — but only after asking you. (Type `/help` to see the other slash commands. Don't use them yet.)

## 4. Read-only tour: ask it to summarize (~15 min)

You're going to use Copilot CLI as a reader, not a writer, today. Type:

> Summarize the structure of this repo. What are the main files, and what does each one do? Don't make any edits.

Read the response carefully. Compare it against what you know is true:

- Are the file descriptions accurate?
- Did it claim a file does something it doesn't?
- Did it miss a file or invent one?

Watch the lines it prints while it works — it shows each file it reads. If it describes a file it never opened, it's guessing.

This is the same calibration exercise as W02D1's first Copilot session — except now Copilot CLI is reading the actual files, not what you pasted. Its accuracy will be different.

## 5. Ask about a specific function (~15 min)

Pick one function from `runner.py`, `fetch.py`, or `parse.py` — ideally the one you struggled to explain in W03D5 prep. Ask:

> Walk through `process_url` (or whatever you picked) line by line. Treat me like someone four weeks into Python.

Read the explanation. For every line:

- Does the explanation match what you understand?
- Is there a line where Copilot's explanation makes more sense than yours?
- Is there a line where Copilot is confidently wrong?

## 6. Notice the temptation to skim a diff (~10 min)

Now ask Copilot CLI to *propose* a small edit — but don't accept it:

> Propose a small improvement to `runner.py` — show me the diff but don't apply it.

When the diff appears, watch what you feel. Is there a pull to skim and say yes? That pull is real. Notice it now, while there's no pressure.

Read every `+` line. If anything is unclear, ask:

> Explain line N of that diff in plain language.

If it goes straight to an approval prompt for the edit, the diff is shown right above it — read it there. Then **reject the change** for today: pick the "No" option (Esc also works). It lets you tell Copilot what to do differently instead; you can just say "skip it for now." You can revisit it tomorrow.

## 7. Exit Copilot CLI, commit nothing (~5 min)

Type `/exit` (or press Ctrl-C twice) to leave the session. There should be nothing to commit — you didn't accept any edits. Run `git status` to confirm:

```
git status
```

Should say "nothing to commit, working tree clean."
